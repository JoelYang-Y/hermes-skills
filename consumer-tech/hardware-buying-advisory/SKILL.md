# 硬件与配件选购咨询

## When to Use（适用）

用户抛来一个具体产品问「怎么样 / 值不值 / 和 X 比怎么选」——表带、手表、椅子、显示器、主机配件。目标是**替他把结论下完**，不是把参数表搬给他。

## 流程（按序执行）

### 1. 先锁定「他现在用的到底是什么」

`mem0_search` 检索设备型号，但**把记忆当线索而不是事实**：

- 一条记忆里常常混着「当前设备」和「历史上的选型讨论」。出现过某型号 ≠ 他已购买该型号。
- 记忆里的型号可能已被他自己换掉。判断依据是两条以上记忆互相印证，或他本次自述。
- 提问里的尺寸/型号族和记忆里的设备对不上时（记忆写 46mm 级机身，他却问该族专属尺寸的配件），**默认记忆过期**：用条件式双分支给结论，或直接问一句「你现在是哪个型号」。
- 一旦发现自己已按旧型号答过，下一轮**开头第一段就显式撤回**（「上一轮那段不适用，撤回」），再给新结论，不要悄悄改写。

### 2. 官网核价核规格（唯一可信价格源）

电商/搜索摘要里的价格全是缓存或第三方，不能当报价。用 `browser_exec`：

```python
new_tab("https://www.apple.com.cn/shop/watch/bands/49mm-titanium")  # 品类页：全部在售款+价格
wait_for_load()
print(js("document.body.innerText")[:4000])
```

- 商品页是 JS 渲染，纯文本抽取常拿不到价格（可能被内网地址判定拒掉或返回空壳）——**直接用 `js("document.body.innerText")` 读渲染后的 DOM**，这一步最稳。
- 品类页拿到价格与在售配色后，再从 `document.querySelectorAll('a')` 里取单品详情页 href，进单品页抓：尺码分档（如 S/M/L 对应腕围毫米区间）、材质百分比、扣合方式、是否限某尺寸表壳。
- 顺带抓「购买页」（`/shop/buy-watch/...`）看**套装是否已含该配件**——随机配件四选一里能选的，单买往往更贵，这是省钱点。

### 3. 官方兼容/规格文档优先于社区说法

机身材质、兼容矩阵这类硬规则只认官方支持文档（Apple 表带兼容：`support.apple.com/zh-cn/108908`）。社区说法用来解释「为什么有人说不兼容」，不用来推翻官方矩阵。

### 4. 社区痛点只取结构性缺点

`web_search` 中文关键词 + Reddit 摘要，过滤掉个体偶发，只留可复现的机制性缺点：夹毛/磨痕/重量/卡扣手感/掉色/刮桌面。带量化数据（克重、续航、价格差）的优先。

### 5. 输出（固定结构，用户偏好）

```
一句话结论（值/不值 + 理由一句）
价格与核价时点（一行）
好在哪 —— 表格：维度 | 实际表现
代价 —— 列表：每条一句机制，不写「可能略有一点点」
针对他这台设备的适配判断 —— 这是全文重点
决定项 —— 尺码/颜色/版本，给推荐值而不是选项清单
结尾最多一个追问
```

## 输出规范

- **必须替他把「值不值」定下来**，并说清是为哪类需求值、为哪类不值。只列参数让他自己选＝没做完。
- 用表格承载对比，不写长段落；关键数字（价格、克重、毫米区间）加粗。
- 每个价格都标「官网现价」并说明是本次抓取；**不引用记忆里的历史价格**，价格会变。
- 涉及尺码/尺寸时按他的体型（187cm / 约 100kg）给出倾向值，但同时要求他实测（腕围、坐深），因为跨档没有补救空间。
- 结论要能落到「买 / 不买 / 买哪个配置」，不落到「看你需求」。

## 陷阱

- **拿记忆当现役设备是最高频错误。** 记忆条目往往把「旧设备事实」和「当时给的选型建议」写在一起，照抄就会给一台他已换掉的机器出适配方案。回答前用一句话确认型号，成本远低于答错重来。
- **官方兼容 ≠ 实际贴合。** Ultra 专属（49mm）表带官方写兼容 44/45/46mm 机身，但社区多例反馈插不到底；原生 49mm 机身则毫无问题。判断「能不能装」之前先问：这是不是它的原生尺寸。
- **不要把某族专属配件套到同品牌其他设备上给建议。** Ultra 表带、Pro 专属笔、Studio 专属支架都属此类。
- **副厂平替的结论要一致**：官方金属件（表带/链带）副厂差价 3–8 倍，但编织密度、卡扣公差、材质纯度差距肉眼可见，用在高端机身上一律不建议；只有纯消耗件才谈平替。
- **别把「昂贵」单独当缺点。** 要换算成占比（配件价 ÷ 机身价）再判断，用户的决策习惯是性价比优先，会自己算这笔账。
