# Pocock 严谨缺陷诊断与排障闭环 (Disciplined Bug Diagnosis)

本技能源自 Matt Pocock 的排障铁律——“绝不在没有可复现的红灯反馈环之前胡乱修改代码（Never guess a fix without a failing test）”。

## When to Use

- 遇到复杂的系统报错、网络异常、构建失败或性能衰退
- 多次尝试修改仍未解决的顽固 Bug
- 排查线上生产环境的非预期行为

## 排障五步法闭环 (The 5-Step Gated Loop)

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│ 1. 构建红灯复现  │ ──> │ 2. 隔离与最小化 │ ──> │ 3. 假设驱动推导 │
│ (Failing Test)  │     │ (Minimise)      │     │ (Hypothesise)   │
└─────────────────┘     └─────────────────┘     └─────────────────┘
                                                         │
                                                         ▼
┌─────────────────┐                             ┌─────────────────┐
│ 5. 回归闭环防重演│ <────────────────────────── │ 4. 插桩与验证修复│
│ (Regression)    │                             │ (Instrument&Fix)│
└─────────────────┘                             └─────────────────┘
```

### 1. 构建红灯反馈环 (Create the Failing Feedback Loop)
- **第一动作**：编写一个能稳定触发报错的测试用例、curl 命令或诊断脚本，亲眼看到它“亮红灯（报错/失败）”。
- **铁律**：严禁在没有可观测的红灯前修改任何业务代码！

### 2. 隔离与最小化上下文 (Minimise Context)
- 剔除无关的干扰因素（如关闭代理、剥离复杂组件、使用最小 input 触发）。
- 将问题范围从“整套大系统”收敛至“某一行代码、某一个 Nginx 指令或某一个环境变量”。

### 3. 提出单一明确假设 (Formulate a Single Hypothesis)
- 严禁一次性修改 5 个地方尝试“碰运气”。
- 每次提出单一假说：“报错是因为 X 导致了 Y”，并设计一个验证方式证明或证伪该假说。

### 4. 插桩、修复与转绿 (Instrument, Fix & Turn Green)
- 在关键路径注入日志或断点确认假说成立；
- 实施最小化精准修改，运行第一步的反馈环，亲眼确认测试“转绿（成功通过）”。

### 5. 回归防重演与经验沉淀 (Regression Prevention)
- 运行全局完整测试，确保没有破坏其他现有功能；
- 将踩坑点与修复经验沉淀至项目的 `CONTEXT.md` 或相关技能文档中。

## 专项：生产者/消费者边界契约故障

当 A 产出的东西被 B 拒收（“返回了非法 X”“格式不对”“无法解析”），且 B 只给出一句笼统错误
时，修 A 的产出格式是错的方向——先确定 B 到底卡在哪一项。

**技巧一：把消费者的校验器搬到手边复刻。**
去读 B 的源码里那个报错字符串的抛出点，把它前面所有 `throw` 条件逐条抄成一个独立脚本，
然后拿 A 的**真实产出**逐项跑，看哪一条先挂：

```python
# 例：逐项复刻下游解析器的每个 throw 条件，定位到具体第几条失败
checks = [
    ("是数组且全为字符串", isinstance(payload, list) and all(isinstance(x, str) for x in payload)),
    ("首项是绝对路径",     os.path.isabs(payload[0])),
    ("'-c' 索引 == len-2", idx >= 1 and idx == len(payload) - 2),
    # ... 把下游每一条 throw 都列上，不要只列你猜的那几条
]
for name, cond in checks: print(("PASS" if cond else "FAIL"), name)
```

价值：把「一句模糊报错」变成「第 5 条挂了」。同时要读懂**失败后下游是回退还是中断**——
很多解析器对“旧版不支持该参数”才回退，其余错误一律 `throw`，于是整个下游直接判不可用。
这是一个独立得多的故障级别，需要在结论里说清楚。

**技巧二：验证生成物必须“真跑一遍”，不能只查格式。**
只要你的修复涉及改写、拼接或生成命令/脚本/载荷，就必须把结果**实际执行一次**。
只做语法/结构校验会放过运行期才炸的错误（拼接出 `;;`、多余转义、变量未展开）——
本类错误在逐项校验里全部 PASS，一执行就 SyntaxError。
两项都做完才算闭环：格式过闸 + 真实跑通。

**技巧三：修复层要选在不会被自动更新冲掉的地方。**
当故障是上下游版本契约错位、而你只能改自己这一侧时，优先在用户自有目录加代理/包装层，
而不是改上游源码（定时自动更新会覆盖或冲突）。把包装层写成**幂等**的：一旦上游修复、
输入已合规就原样透传，等于自我注销；并对任何解析异常一律原样透传，绝不破坏正常输入。
